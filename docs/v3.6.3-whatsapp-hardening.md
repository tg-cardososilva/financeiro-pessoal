# v3.6.3 — Hardening do WhatsApp

Baseline: v3.6.2.

Esta versão endurece exclusivamente o webhook `jarvis-whatsapp-webhook`. Não altera WABA, número, fluxo de ativação, escopos, regras de negócio, frontend, Google Calendar, Google Drive, Document AI, Tarefas, Notas, Projetos ou Finanças.

## Estado de produto preservado

- O número de produção continua no estado operacional existente (`Pendente`).
- Nenhuma tentativa de registro/reativação é feita por esta versão.
- `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, WABA ID e demais credenciais existentes não são rotacionados.
- `jarvis-whatsapp-send` permanece inalterado.
- `verify_jwt=false` continua intencional no webhook, porque a Meta precisa alcançar GET/POST sem JWT Supabase. A autenticação do POST é feita pela assinatura da Meta.

## GET de verificação

O fluxo existente é preservado:

1. lê `hub.mode`, `hub.verify_token` e `hub.challenge`;
2. exige `hub.mode=subscribe`;
3. compara o verify token com `WHATSAPP_VERIFY_TOKEN`;
4. devolve o challenge com HTTP 200 quando correto;
5. retorna 403 quando a verificação é inválida.

O verify token nunca é escrito em log.

## Assinatura do POST

Todo POST exige `X-Hub-Signature-256` no formato:

`sha256=<64 caracteres hexadecimais>`

O backend:

1. lê o corpo bruto como bytes;
2. calcula HMAC-SHA256 com `WHATSAPP_APP_SECRET`;
3. compara os 32 bytes em tempo constante, sem early return por byte;
4. somente após assinatura válida decodifica e faz `JSON.parse`;
5. rejeita assinatura ausente, malformada, inválida ou corpo adulterado antes de qualquer claim/processamento.

O App Secret existe somente em Supabase Edge Function Secrets e é lido por `Deno.env`. Ele não pode aparecer no frontend, banco, repositório, resposta HTTP ou logs.

Se `WHATSAPP_APP_SECRET` não estiver configurado, o POST falha fechado com HTTP 503 e nenhuma mensagem é processada.

## Idempotência

Tabela interna: `public.jarvis_whatsapp_webhook_events`.

Ela armazena somente:

- `event_key_hash`: SHA-256 de uma chave estável do evento;
- `event_kind`: `message`, `status` ou `event`;
- timestamps de criação e expiração.

Nunca armazena payload, texto da mensagem, telefone, nome de contato, token, assinatura ou headers.

Estratégia de chave:

- mensagem: message ID;
- status: message ID + status;
- evento sem identificador específico: hash determinístico do corpo bruto.

A chave original é novamente hasheada antes de persistir. A unique/primary key garante deduplicação concorrente entre instâncias da Edge Function.

Retenção: 7 dias. A remoção de entradas expiradas é oportunística em POSTs válidos, sem cron ou scheduler adicional.

A tabela é backend-only:

- RLS habilitado;
- zero policies;
- zero grants para `anon`;
- zero grants para `authenticated`;
- somente `service_role` recebe `SELECT`, `INSERT` e `DELETE`.

## Logs

Foram removidos os logs diagnósticos que continham payload integral, telefone, texto, contato, recipient ID, conversation e outros objetos detalhados.

Os logs finais contêm apenas eventos operacionais mínimos, por exemplo:

- resultado do GET de verificação sem o token;
- motivo categórico de rejeição da assinatura;
- contagem de entries/changes/messages/statuses;
- nomes de campos de evento, como `messages`;
- contagem de eventos novos e duplicados;
- código técnico de erro de banco quando existir.

Não são logados:

- App Secret;
- verify token;
- assinatura recebida;
- Authorization/apikey headers;
- corpo bruto;
- payload integral;
- texto de mensagem;
- telefone;
- nome/wa_id de contato.

## Falha segura

- assinatura inválida/ausente/malformada: HTTP 401;
- App Secret ausente: HTTP 503;
- JSON inválido ou shape incompatível com webhook WhatsApp: HTTP 400;
- payload acima de 3 MiB: HTTP 413;
- falha de idempotência/banco: HTTP 500, para permitir retry legítimo da Meta sem processar de forma insegura;
- replay já registrado: HTTP 200 com `duplicate=true`, sem novo processamento.

## Compatibilidade futura com Jarvis

Esta versão não adiciona resposta automática nem chama `jarvis-core` a partir do webhook.

Quando o processamento de mensagens for autorizado no futuro, qualquer regra de negócio deve ser adicionada somente após:

1. assinatura válida;
2. payload válido;
3. claim idempotente marcado como novo.

Retries/replays nunca devem disparar uma segunda ação/resposta.

## Testes v3.6.3

Fixtures sintéticas cobrem:

- GET correto;
- GET com verify token inválido;
- POST com assinatura válida;
- assinatura inválida;
- ausência de assinatura;
- corpo adulterado depois de assinado;
- formato de assinatura inválido;
- replay do mesmo message/event ID;
- JSON malformado;
- evento de status legítimo sem mensagem;
- App Secret ausente;
- guardrail de logs sem conteúdo sensível.

Os testes automatizados usam apenas `Request` sintético e idempotência em memória. Nenhuma mensagem é enviada pela Meta e nenhuma fixture é persistida em produção.

## Validação final

Após a configuração manual de `WHATSAPP_APP_SECRET` em Supabase Edge Function Secrets, o probe live deixou de retornar `503 webhook_not_configured` e passou a rejeitar uma assinatura deliberadamente inválida com HTTP 401 `signature_invalid`. O GET live com verify token deliberadamente incorreto permaneceu em HTTP 403.

A suíte final passou 12/12 testes, `deno check`, `git diff --check`, guardrails de logs e secret leak. A tabela de idempotência ficou com 0 registros artificiais. Os 9 `financial_documents`, 176 `transactions`, Calendar e a pasta `Meu Drive / JARVIS` permaneceram inalterados e acessíveis.

O Security Advisor lista `jarvis_whatsapp_webhook_events` como `RLS enabled no policy`. Isso é intencional para uma tabela backend-only: RLS ligado, nenhuma policy e nenhum grant para `anon` ou `authenticated`. O aviso de leaked-password protection e os avisos históricos de performance permanecem conforme documentado na v3.6.2.

## Cache-bust

Nenhum arquivo web é modificado. O cache-bust permanece v3.6.1, que continua sendo a versão visual/frontend vigente.
